# Техническая статья по коду проекта

## 1. О чем этот проект

Проект представляет собой интеллектуальную систему поддержки принятия решений при покупке жилья. Если говорить простыми словами, система помогает пользователю выбрать квартиру не только по фильтрам вроде цены и площади, но и с учетом того, насколько объект выглядит разумным по рынку.

Обычный сайт объявлений показывает пользователю много вариантов. В этом проекте задача другая: взять большой массив объявлений, обработать его, оценить рыночную стоимость объектов, применить рекомендательные алгоритмы и сформировать короткий список наиболее подходящих вариантов.

Итог работы системы - `shortlist`, то есть небольшой список объектов, которые лучше всего подходят под пользовательские предпочтения и одновременно выглядят привлекательными с точки зрения рыночной оценки.

## 2. Общий принцип работы

Код устроен как последовательный конвейер. Каждый этап берет результат предыдущего этапа, обрабатывает его и сохраняет свои выходные файлы.

Общий путь данных такой:

```text
исходные CSV-файлы
-> объединение данных
-> исследовательский анализ
-> очистка и предобработка
-> обучение моделей цены
-> оценка моделей
-> создание дополнительных признаков
-> рекомендательные алгоритмы
-> итоговый DSS-shortlist
-> отчеты, таблицы и графики
```

Такой подход удобен, потому что каждый этап можно отдельно проверить, объяснить и при необходимости заменить.

## 3. Главный файл проекта

Главная точка входа находится в `main.py`.

Этот файл не содержит всю логику проекта внутри себя. Его задача - запускать нужные этапы. Например:

```bash
python main.py --run-preprocessing
python main.py --run-price-models
python main.py --run-hybrid
python main.py --run-decision-support
```

То есть `main.py` работает как диспетчер. Он создает конфигурацию, подготавливает директории, настраивает логи и запускает выбранные блоки.

Главная идея архитектуры: каждый большой этап оформлен отдельным классом с методом `execute()`. Это делает код понятным: если нужно запустить предобработку, вызывается `RealEstatePreprocessor.execute()`, если нужно обучить модели - `PriceModelTrainer.execute()`, если нужно построить итоговый список - `DecisionSupportEngine.execute()`.

## 4. Конфигурация проекта

Все основные настройки находятся в `config/config.py`.

Там задаются:

1. пути к папкам проекта;
2. имена входных и выходных файлов;
3. параметры очистки данных;
4. параметры моделей;
5. размеры выборок;
6. настройки рекомендательных алгоритмов;
7. веса итогового ранжирования.

Это сделано для того, чтобы не хранить настройки внутри алгоритмов. Если нужно изменить размер выборки, имя файла или веса гибридной рекомендации, это делается в одном месте.

Преимущество такого подхода: код становится более аккуратным, а эксперименты легче повторять.

## 5. Загрузка и объединение данных

За загрузку данных отвечает модуль `src/preprocessing/data_loader.py`.

Он ищет CSV-файлы, определяет их кодировку, разделитель и структуру колонок. Это важно, потому что исходные данные могут приходить из разных источников и иметь немного разные названия столбцов.

За объединение отвечает `src/preprocessing/data_merger.py`.

Там реализован класс `SchemaHarmonizer`. Его задача - привести разные датасеты к единой схеме. Например, если в одном файле колонка называется `rooms`, а в другом `Number of rooms`, система сопоставляет их с единым каноническим названием.

Почему это важно:

1. разные источники данных могут иметь разные названия колонок;
2. модели должны получать единую структуру данных;
3. после объединения становится проще делать анализ и обучение.

На выходе получается общий файл `merged_data.csv`.

## 6. Исследовательский анализ данных

Модуль `src/preprocessing/eda_analyzer.py` отвечает за EDA, то есть первичный анализ данных.

На этом этапе система смотрит:

1. сколько всего строк и колонок;
2. где есть пропуски;
3. какие распределения у числовых признаков;
4. какие категории встречаются чаще;
5. как цена связана с площадью, районом и другими признаками;
6. есть ли дубликаты или подозрительные значения.

EDA нужен не просто для красивых графиков. Он помогает понять, какие проблемы есть в данных до обучения моделей.

Например, если в данных есть квартиры с нулевой площадью или слишком большой ценой, модель может обучиться неправильно. Поэтому сначала нужно увидеть такие проблемы, а затем обработать их.

## 7. Очистка и предобработка данных

Модуль `src/preprocessing/preprocessor.py` реализует очистку и подготовку данных для моделей.

На этом этапе происходит несколько важных вещей.

Сначала удаляются явно некорректные строки. Например:

1. цена слишком маленькая или слишком большая;
2. площадь выходит за разумные границы;
3. число комнат некорректное;
4. этаж больше количества этажей в доме;
5. этажность или этаж имеют невозможные значения.

Затем пропуски заполняются:

1. числовые признаки - медианой;
2. категориальные признаки - наиболее частым значением.

После этого категориальные признаки кодируются численно. Это нужно потому, что модели машинного обучения не умеют напрямую работать со строками вроде названия метро или типа ремонта.

В проекте используется frequency encoding. Это значит, что категория заменяется на частоту ее появления в данных. Например, если определенный район встречается часто, он получает более высокое числовое значение.

Также числовые признаки масштабируются:

1. `StandardScaler` приводит признаки к сопоставимому масштабу;
2. `MinMaxScaler` нормализует значения в диапазон.

На выходе формируются:

1. очищенный файл `clean_data.csv`;
2. модельный набор `modeling_dataset.csv`;
3. обучающая выборка `train_data.csv`;
4. тестовая выборка `test_data.csv`.

## 8. Почему используется разделение на train и test

Модель нельзя проверять на тех же данных, на которых она обучалась. Иначе она может просто "запомнить" примеры, а не научиться обобщать.

Поэтому данные делятся на две части:

1. `train` - для обучения;
2. `test` - для проверки качества.

В проекте используется классическое разделение 80 на 20. Это означает, что большая часть данных идет на обучение, а отдельная часть остается для честной оценки.

## 9. Модели оценки рыночной стоимости

Модели реализованы в `src/models/price_model.py`.

В проекте сравниваются три модели:

1. `Linear Regression`;
2. `Random Forest Regressor`;
3. `Gradient Boosting Regressor`.

### Linear Regression

Линейная регрессия используется как базовая модель. Она простая и хорошо объяснимая.

Почему она была взята:

1. нужна точка сравнения;
2. можно понять, насколько сложные модели лучше простого подхода;
3. она быстро обучается.

Минус линейной регрессии в том, что она плохо описывает сложные нелинейные зависимости.

### Random Forest Regressor

Random Forest - это ансамбль решающих деревьев. Он строит много деревьев и усредняет их ответы.

Почему он хорошо подходит:

1. хорошо работает с табличными данными;
2. умеет учитывать нелинейные зависимости;
3. устойчив к шуму;
4. позволяет оценить важность признаков.

В проекте именно Random Forest показал лучший результат по оценке стоимости, поэтому он используется дальше в DSS-контуре.

### Gradient Boosting Regressor

Gradient Boosting тоже является ансамблевым методом, но строит деревья последовательно: каждое новое дерево пытается исправить ошибки предыдущих.

Почему он был взят:

1. это сильный метод для табличных данных;
2. он часто показывает высокое качество;
3. его полезно сравнить с Random Forest.

В данном проекте он оказался полезным для сравнения, но лучшим по результатам стал Random Forest.

## 10. Метрики оценки моделей цены

Для оценки моделей используются несколько метрик.

### RMSE

RMSE показывает среднюю ошибку прогноза с усиленным штрафом за крупные ошибки.

Почему она важна:

1. цена недвижимости измеряется в рублях;
2. крупные ошибки особенно нежелательны;
3. метрика хорошо показывает практический масштаб ошибки.

Если RMSE меньше, модель лучше.

### R²

R² показывает, насколько хорошо модель объясняет разброс цен в данных.

Если R² ближе к 1, модель лучше объясняет данные.

Почему нужен R²:

1. RMSE показывает ошибку в рублях;
2. R² показывает общее качество объяснения цены;
3. вместе они дают более полную картину.

### MAE и MSE

MAE показывает среднюю абсолютную ошибку. MSE показывает среднюю квадратичную ошибку.

Они используются как дополнительные метрики, чтобы сравнение моделей было более полным.

## 11. Инженерия признаков

Модуль `src/feature_engineering/feature_builder.py` создает дополнительные признаки, которые лучше отражают предметную область недвижимости.

Были разработаны такие признаки:

1. `price_per_m2` - цена за квадратный метр;
2. `floor_ratio` - относительная позиция этажа в доме;
3. `floor_comfort_score` - комфортность этажа;
4. `transport_score` - транспортная доступность;
5. `renovation_score` - оценка ремонта;
6. `district_popularity_score` - популярность района;
7. `liquidity_score` - ликвидность объекта;
8. `investment_score` - инвестиционная привлекательность.

Зачем это нужно:

1. исходные признаки не всегда напрямую отражают качество объекта;
2. доменные признаки помогают лучше описать объект;
3. часть признаков полезна для рекомендаций и итогового ранжирования.

Например, `transport_score` превращает информацию о метро и времени до метро в понятный числовой показатель. `investment_score` объединяет несколько характеристик, которые могут говорить о перспективности объекта.

Важно: `price_per_m2` используется осторожно, потому что он зависит от цены. Если использовать его неправильно при прогнозировании цены, может возникнуть утечка целевой переменной.

## 12. Рекомендательные алгоритмы

Рекомендательные методы находятся в папке `src/recommendation/`.

В проекте реализованы четыре подхода:

1. content-based;
2. collaborative filtering;
3. knowledge-based;
4. hybrid.

## 13. Content-based рекомендации

Content-based подход сравнивает характеристики объектов с профилем пользователя.

Например, пользователь хочет:

1. бюджет до определенной суммы;
2. площадь около 45 м²;
3. 2 комнаты;
4. определенное метро;
5. хороший ремонт;
6. высокий инвестиционный и ликвидный потенциал.

Система считает, насколько каждый объект похож на такой профиль.

В проекте сравнивались разные способы похожести:

1. cosine similarity;
2. euclidean similarity;
3. manhattan similarity;
4. weighted similarity.

Лучшим оказался `content_weighted`.

Почему именно он:

1. в недвижимости признаки имеют разную важность;
2. цена и площадь обычно важнее второстепенных параметров;
3. веса позволяют лучше приблизить алгоритм к логике реального выбора.

Преимущество метода: он понятный и хорошо работает, когда у объектов есть структурированные характеристики.

## 14. Collaborative filtering

Collaborative filtering обычно использует поведение пользователей: просмотры, оценки, лайки, покупки.

В проекте реальных пользовательских действий не было, поэтому были созданы синтетические взаимодействия. Это нужно было, чтобы показать, как такой подход может быть встроен в систему.

Преимущество collaborative filtering:

1. он может находить скрытые закономерности в поведении пользователей;
2. он полезен, когда есть много реальных взаимодействий.

Ограничение в этой работе:

1. взаимодействия синтетические;
2. поэтому коллаборативный сигнал получился слабее;
3. для реального улучшения нужны настоящие пользовательские данные.

Это честное ограничение проекта, и его можно спокойно объяснять комиссии.

## 15. Knowledge-based рекомендации

Knowledge-based подход работает на правилах.

Сначала система применяет жесткие фильтры:

1. объект должен проходить по бюджету;
2. площадь должна быть в нужном диапазоне;
3. число комнат должно подходить;
4. транспортная доступность должна быть не ниже заданного уровня;
5. инвестиционный и ликвидный показатели должны быть достаточно высокими.

Преимущество метода:

1. он легко объясняется;
2. хорошо соблюдает ограничения;
3. подходит для задач, где важны жесткие требования пользователя.

Минус: такой подход может быть менее гибким, чем content-based. Если правила слишком строгие, хороших объектов может остаться мало.

## 16. Hybrid рекомендации

Hybrid подход объединяет несколько источников сигнала:

1. цену;
2. транспорт;
3. ремонт;
4. инвестиционность;
5. комфортность этажа;
6. ликвидность;
7. content-based похожесть;
8. collaborative-сигнал.

Итоговый гибридный score считается как взвешенная сумма компонентов.

Почему был взят hybrid:

1. он позволяет объединить сильные стороны разных методов;
2. учитывает объект с нескольких сторон;
3. хорошо подходит для DSS-задачи.

Почему hybrid не стал лучшим по всем метрикам:

1. коллаборативный сигнал был слабым;
2. реальные пользовательские данные отсутствовали;
3. content_weighted оказался более стабильным именно в текущей постановке.

Это нормальный результат: гибридный метод не обязан всегда побеждать. Его качество зависит от качества входящих компонентов.

## 17. Оценка рекомендательных алгоритмов

Оценка рекомендаций находится в `src/evaluation/recommendation_evaluator.py`.

Используются две важные идеи:

1. насколько объект полезен пользователю;
2. насколько высоко он стоит в списке.

Главная метрика - `DCG utility`.

Почему она выбрана:

1. в рекомендациях важен порядок;
2. хороший объект на первом месте полезнее, чем хороший объект в конце;
3. DCG учитывает позицию объекта.

Также используется `hard_constraint_rate`.

Она показывает, насколько метод соблюдает жесткие ограничения пользователя. Это важно, потому что рекомендация бесполезна, если объект не проходит по бюджету или другим обязательным условиям.

## 18. Итоговый DSS-контур

Итоговая система находится в `src/experiments/decision_support.py`.

На этом этапе происходит главное объединение:

1. берется профиль пользователя;
2. отбираются подходящие кандидаты;
3. считается content-based соответствие;
4. загружается модель Random Forest;
5. прогнозируется рыночная стоимость;
6. считается относительная недооцененность;
7. рассчитывается итоговый `decision_support_score`;
8. формируется shortlist.

Итоговый score объединяет:

1. соответствие предпочтениям пользователя;
2. рыночную привлекательность;
3. инвестиционный потенциал;
4. ликвидность.

Это и есть основная идея DSS: не один показатель решает все, а несколько факторов объединяются в итоговую оценку.

## 19. Что такое relative_discount_to_market

Это показатель, который сравнивает цену объявления с прогнозной рыночной стоимостью.

Если прогнозная рыночная стоимость выше цены объявления, объект выглядит потенциально недооцененным.

Простыми словами:

```text
модель считает, что объект может стоить дороже,
чем его текущая цена в объявлении
```

Важно понимать: это не гарантия выгоды. Это аналитический сигнал, который помогает обратить внимание на объект.

## 20. Графики и таблицы

Проект автоматически сохраняет много графиков и таблиц в `reports/plots/` и `reports/tables/`.

Графики нужны для объяснения результатов:

1. распределение цен показывает структуру рынка;
2. графики до и после очистки показывают эффект предобработки;
3. сравнение моделей показывает, почему выбран Random Forest;
4. важность признаков показывает, на что опирается модель;
5. сравнение рекомендаций показывает, почему выбран content_weighted;
6. графики hybrid-компонентов показывают вклад разных сигналов;
7. графики DSS показывают итоговый shortlist и рыночную недооцененность.

Таблицы нужны для точных числовых результатов и приложений к ВКР.

## 21. Почему код устроен именно так

Код разделен на модули не случайно.

Такой подход дает несколько преимуществ:

1. понятность - каждый файл отвечает за свою часть;
2. проверяемость - каждый этап сохраняет результаты;
3. расширяемость - можно заменить модель или алгоритм;
4. воспроизводимость - результаты можно повторить;
5. удобство защиты - легко объяснить путь от данных до итогового списка.

Главная архитектурная идея: проект работает не как один большой скрипт, а как система взаимосвязанных этапов.

## 22. Что важно запомнить для предзащиты

Самое главное:

1. проект решает задачу выбора жилья как многокритериальную задачу;
2. данные проходят полный путь от очистки до итогового shortlist;
3. Random Forest выбран потому, что лучше показал себя в оценке цены;
4. RMSE и R² нужны для оценки модели стоимости;
5. content_weighted выбран потому, что лучше ранжировал рекомендации;
6. DCG utility нужна, потому что важен порядок объектов в списке;
7. knowledge-based и hybrid хорошо соблюдают жесткие ограничения;
8. DSS-score объединяет предпочтения пользователя и рыночную привлекательность;
9. collaborative filtering ограничен из-за отсутствия реальных пользовательских данных;
10. итог работы - shortlist из объектов, которые пользователь может рассматривать в первую очередь.

## 24. Короткий ответ на вопрос "почему выбраны именно эти методы"

Были выбраны не случайные методы, а набор, который позволяет сравнить разные подходы.

Для цены:

1. Linear Regression - простая базовая модель;
2. Random Forest - сильная модель для табличных данных;
3. Gradient Boosting - еще один сильный ансамблевый метод для сравнения.

Для рекомендаций:

1. content-based - хорошо работает по характеристикам объектов;
2. collaborative - показывает подход на основе пользовательского поведения;
3. knowledge-based - хорошо соблюдает явные правила;
4. hybrid - объединяет несколько сигналов.

Для метрик:

1. RMSE - показывает ошибку цены в рублях;
2. R² - показывает качество объяснения цены;
3. DCG utility - оценивает полезность ранжированного списка;
4. hard_constraint_rate - проверяет соблюдение жестких ограничений;
5. decision_support_score - итоговая оценка объекта для shortlist.

Такой набор позволяет не только получить результат, но и обосновать, почему итоговая система устроена именно так.
