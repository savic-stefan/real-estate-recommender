# Руководство по коду и архитектуре проекта

## 1. Назначение проекта

Проект реализует интеллектуальную систему поддержки принятия решений при покупке жилья. Система решает сразу несколько задач:

1. объединяет несколько исходных CSV-датасетов рынка недвижимости;
2. очищает и нормализует данные;
3. обучает модели прогнозирования рыночной стоимости объекта;
4. строит инженерные признаки предметной области;
5. сравнивает несколько рекомендательных подходов;
6. формирует итоговый shortlist объектов для пользователя;
7. автоматически собирает аналитические и защитные материалы для ВКР.

Идея проекта не сводится к одному алгоритму. Это последовательный исследовательский пайплайн, где каждый этап подготавливает артефакты для следующего.

## 2. Общая архитектура

Проект построен как модульный конвейер. Главная точка входа находится в [main.py](/C:/Users/Stefan/Desktop/diplom/main.py). Она не содержит бизнес-логики алгоритмов, а только оркестрирует этапы.

Архитектура делится на слои:

1. `config/`  
   Централизованные настройки путей, этапов, моделей, экспериментов и весов.

2. `src/preprocessing/`  
   Загрузка исходных CSV, harmonization схем, EDA, очистка и подготовка моделирующего набора.

3. `src/models/`  
   Обучение регрессионных моделей стоимости жилья и их оценка.

4. `src/feature_engineering/`  
   Генерация доменных признаков: транспортная доступность, ликвидность, инвестиционная привлекательность и др.

5. `src/recommendation/`  
   Реализация content-based, collaborative, knowledge-based и hybrid рекомендаций.

6. `src/evaluation/`  
   Единая офлайн-оценка рекомендательных методов.

7. `src/experiments/`  
   Интеграционные сценарии: decision support, final demo, final analytics, defense preparation.

8. `src/visualization/`  
   Генерация графиков для EDA, моделей, рекомендаций, итоговой аналитики и защиты.

9. `src/utils/`  
   Общие функции: логирование, создание директорий, сериализация JSON, поиск файлов.

10. `reports/`, `artifacts/`, `data/`  
    Выходные таблицы, графики, metadata, модели и подготовленные наборы данных.

## 3. Жизненный цикл данных

Полный поток данных выглядит так:

`raw CSV -> merged_data.csv -> clean_data.csv -> modeling_dataset/train/test -> price models -> engineered_data.csv -> recommendation results -> evaluation -> shortlist -> demo/analytics/defense artifacts`

Важная особенность проекта: почти каждый этап сохраняет результат на диск, а не передаёт всё только в памяти. Это повышает воспроизводимость, упрощает отладку и делает работу удобной для ВКР.

### 6.2. Объединение и harmonization: `data_merger.py`

Файл [src/preprocessing/data_merger.py](/C:/Users/Stefan/Desktop/diplom/src/preprocessing/data_merger.py) реализует `SchemaHarmonizer`.

Логика этапа:

1. читаются профили всех сырых датасетов;

   `dataset_schema_comparison.csv` и `dataset_column_mappings.csv`;
5. все данные потоково объединяются в `merged_data.csv`;
6. добавляются metadata-поля:
   `Source dataset`, `Source file`, `Source row number`.

Ключевые методы:

1. `execute()`  
   Полный merge-конвейер.

2. `_prepare_schema_reports()`  
   Готовит таблицы покрытия и сопоставления схем.

3. `_analyze_profile()`  
   Определяет, какие колонки совпали с canonical schema, какие отсутствуют, какие extra.

4. `_merge_datasets()`  
   Пишет единый CSV чанками.

5. `_harmonize_chunk()`  
   Переименовывает колонки, добавляет metadata, выравнивает схему.

### 6.4. Очистка и подготовка модельных данных: `preprocessor.py`

Файл [src/preprocessing/preprocessor.py](/C:/Users/Stefan/Desktop/diplom/src/preprocessing/preprocessor.py) реализует `RealEstatePreprocessor`.

Это один из ключевых модулей проекта.

Этап состоит из двух проходов по данным:

1. Первый проход:
   собирает статистику, считает пропуски, фиксирует срабатывания правил очистки, строит медианы и моды для импутации.

2. Второй проход:
   реально очищает данные, заполняет пропуски и сохраняет `clean_data.csv`.

После этого:

1. кодируются категориальные признаки через frequency encoding;
2. числовые признаки стандартизируются через `StandardScaler`;
3. строятся также normalized-признаки через `MinMaxScaler`;
4. сохраняется `modeling_dataset.csv`;
5. выполняется разбиение на `train_data.csv` и `test_data.csv`.

Ключевые методы:

1. `_collect_global_statistics()`  
   Первый проход по данным.

2. `_apply_row_filters()`  
   Набор бизнес-правил очистки.

3. `_apply_imputation()`  
   Заполнение пропусков медианой и модой.

4. `_encode_categorical_columns()`  
   Frequency encoding для категориальных полей.

5. `_add_scaled_features()`  
   Добавляет признаки вида `_scaled`.

6. `_normalize_numeric_features()`  
   Добавляет признаки вида `_normalized`.

7. `_select_numeric_modeling_frame()`  
   Формирует окончательный набор model-ready признаков.

### 6.5. Какие правила очистки реализованы

Жёстко фильтруются:

1. цена вне допустимого диапазона;
2. площадь вне допустимого диапазона;
3. число комнат вне диапазона;
4. этаж вне диапазона;
5. этажность вне диапазона;
6. случаи, когда этаж выше этажности здания.

Не удаляются, а переводятся в `NaN`:

1. некорректная площадь кухни;
2. некорректная жилая площадь;
3. некорректные минуты до метро.

Это важно для ответа на защите: проект различает критические ошибки строки и исправимые локальные аномалии.

### 8.2. Как выбираются признаки

Метод `_resolve_feature_columns()` берёт только признаки с суффиксами:

1. `Price`
2. `Price_scaled`
3. `Price_normalized`

Это важно для ВКР: целевая переменная не попадает обратно в вход модели.

## 11. Рекомендательные алгоритмы

## 11.1. Content-based recommendation

Файл [src/recommendation/content_based.py](/C:/Users/Stefan/Desktop/diplom/src/recommendation/content_based.py) реализует `ContentBasedRecommender`.

Профиль пользователя задаётся классом `UserPreferenceProfile`:

1. бюджет;
2. желаемая площадь;
3. число комнат;
4. предпочтительное метро;
5. предпочтительный ремонт;
6. целевые `investment_score` и `liquidity_score`.

Сравниваются четыре метода:

1. cosine similarity
2. euclidean similarity
3. manhattan similarity
4. weighted similarity

### Почему weighted similarity победил

Он лучше отражает прикладную логику выбора жилья, потому что:

1. учитывает бизнес-важность признаков;
2. не делает все характеристики равноправными;
3. сочетает числовые и категориальные признаки в понятной формуле.

### Формула weighted similarity

Используется взвешенная сумма:

1. близость по цене;
2. близость по площади;
3. близость по комнатности;
4. совпадение метро;
5. совпадение ремонта;
6. близость инвестиционного потенциала;
7. близость ликвидности.

Для числовой близости используется универсальная функция:

`bounded_closeness = 1 / (1 + abs(value - target) / scale)`

Она нормирует сходство в диапазон `[0, 1]`.

## 11.2. Collaborative filtering

Файл [src/recommendation/collaborative.py](/C:/Users/Stefan/Desktop/diplom/src/recommendation/collaborative.py) реализует `CollaborativeFilteringRecommender`.

Так как реальных пользовательских логов нет, используются синтетические взаимодействия.

### Что сделано

1. генерируются mock user profiles;
2. для каждого пользователя вычисляется preference-driven score;
3. на его основе создаются synthetic ratings;
4. строится матрица user-item;
5. сравниваются:
   `user_based_cf` и `item_based_cf`.

### Почему это допустимо для ВКР

Это не промышленная рекомендация, а исследовательский стенд, который демонстрирует:

1. архитектуру collaborative filtering;
2. принцип формирования матрицы взаимодействий;
3. ограничения метода при отсутствии реальных логов.

На защите нужно честно говорить, что collaborative-часть ограничена синтетической обратной связью.

7. минимальный `transport_score`.

### Optional rules

1. предпочтительное метро;
2. предпочтительный ремонт;
3. известное метро;
4. известный ремонт.

Optional rules применяются только если после них остаётся достаточно кандидатов.  
Это защита от чрезмерного сужения выборки.

### Почему метод хорош для ВКР

1. он интерпретируем;
2. позволяет объяснить каждый шаг фильтрации;
3. даёт удобную воронку для графиков;
4. хорошо подходит для принятия решений под ограничениями.

## 11.4. Hybrid recommendation

Файл [src/recommendation/hybrid.py](/C:/Users/Stefan/Desktop/diplom/src/recommendation/hybrid.py) реализует `HybridRecommender`.

Гибрид объединяет:

1. knowledge gate;
2. content score;
3. collaborative score;
4. доменные компоненты качества объекта.

### Компоненты гибридного скоринга

1. `price_component`
2. `transport_component`
3. `renovation_component`
4. `investment_component`
5. `floor_component`
6. `liquidity_component`
7. `similarity_component`
8. `collaborative_component`

Итог:

`hybrid_score = Σ weight_i * component_i`

Весовые коэффициенты берутся из `RecommendationWeights`.

### Почему hybrid не обязательно лучший

Гибридный метод не гарантированно обгоняет content-based.  
Если collaborative signal слабый, а rule gate уже жёстко отсёк хорошие варианты, итоговый прирост может быть небольшим. Это как раз и показано результатами проекта.

## 13. Интегрированная система поддержки решения

### 13.1. `decision_support.py`

Файл [src/experiments/decision_support.py](/C:/Users/Stefan/Desktop/diplom/src/experiments/decision_support.py) реализует `DecisionSupportEngine`.

Это кульминационный этап проекта.

### 13.2. Что делает DSS

1. берёт engineered dataset;
2. формирует feasible candidate pool;
3. считает preference score по content-like логике;
4. загружает лучшую модель цены;
5. оценивает `predicted_market_price`;
6. считает недооценённость объекта относительно рынка;
7. объединяет preference fit, valuation, investment и liquidity;
8. формирует итоговый shortlist.

### 13.3. Как работает рыночная оценка

Используется ранее обученная модель `RandomForestPriceModel`, а также:

1. frequency encoders;
2. standard scaler;
3. сохранённый feature schema.

Это позволяет воспроизвести те же признаки, на которых обучалась модель.

### 13.4. Какие score используются в DSS

1. `preference_score`
2. `valuation_score`
3. `investment_score_component`
4. `liquidity_score_component`
5. `decision_support_score`

Итоговая формула:

`0.42 * preference + 0.30 * valuation + 0.16 * investment + 0.12 * liquidity`

### 13.5. Как интерпретировать `relative_discount_to_market`

Это отношение разницы:

`predicted_market_price - asking_price`

к предсказанной рыночной цене.

Если показатель положительный, объект выглядит дешевле, чем ожидает модель.  
То есть с точки зрения системы он может быть недооценён рынком.

### 13.6. Зачем нужен `explanation`

Поле `explanation` собирает короткие причины, почему объект попал в shortlist:

1. ниже оценочной рыночной цены;
2. сильное совпадение с предпочтениями;
3. совпадение по метро;
4. совпадение по ремонту;
5. высокий investment score;
6. высокая liquidity.

Это объяснимый слой поверх численного скоринга.

## 24. Типовые вопросы комиссии и краткие ответы

### Почему проект не ограничился одной моделью?

Потому что задача ВКР исследовательская. Нужно не просто получить результат, а сравнить альтернативы и обосновать выбор лучшего решения.

### Почему выбран Random Forest?

Потому что по итогам holdout-оценки и cross-validation он показал лучшую точность и лучше уловил нелинейные зависимости рынка недвижимости.

### Почему content-based оказался сильнее hybrid?

Потому что collaborative-сигнал строился на синтетических взаимодействиях и оказался слабее, чем прямое сравнение объектов с профилем пользователя.

### Почему knowledge-based всё ещё полезен?

Потому что он максимально интерпретируем и хорошо работает как explainable filtering layer.

### Зачем нужен DSS, если уже есть recommendation?

Recommendation отвечает на вопрос "что похоже на предпочтения пользователя", а DSS отвечает на более прикладной вопрос "что не только подходит, но и может быть выгодным с точки зрения рыночной оценки".

### Почему проект обрабатывает данные чанками?

Потому что исходные CSV очень большие, и потоковая обработка делает систему устойчивой по памяти и ближе к реальным сценариям работы с большими данными.
